## 1. Введение

**Kemano Transfer Cargo v2.0** — транспортный протокол реального времени поверх UDP, предназначенный для обхода систем глубокой инспекции пакетов (DPI) и средств активного противодействия (ТСПУ).

### 1.1. Ключевое отличие от v1.9

v2.0 — это **полный перенос кодовой базы на C11** без изменения формата протокола. Python-прототип v1.9 удалён, вся логика переписана на нативном C с единственной зависимостью — libsodium.

### 1.2. Что сохранилось

- Формат пакетов KTC0/KTCA (156/108 байт)
- Криптографические примитивы (ChaCha20-Poly1305, X25519, BLAKE2b, HMAC-SHA256)
- Слепое рукопожатие
- 11 профилей маскировки
- 8 параллельных потоков
- BBR-контроль перегрузки
- Selective ACK
- Обход белых списков через Cloudflare Spectrum

### 1.3. Совместимость

Клиент v1.9 (Python) **совместим** с сервером v2.0 (C) и наоборот. Протокол на проводе не изменился.

## 4. Архитектура

### 4.1. Транспортный уровень

Протокол работает поверх **UDP**. Порт сервера — `GUARD_PORT`.

**Причины выбора UDP:**
- Нет флагов состояния (SYN, RST, FIN)
- Невозможность инжекта RST
- Сложность отличения от WebRTC / QUIC / STUN
- Нативная поддержка в CDN

### 4.2. Три слоя защиты

```

┌─────────────────────────────────────────┐
│              Слой 1: Транспорт           │
│  UDP-датаграммы, зашифрованный шум      │
│  Маскировка под HTTP/3, WebRTC, STUN    │
├─────────────────────────────────────────┤
│              Слой 2: Рукопожатие         │
│  KTC0 / KTCA, зашифрованы на            │
│  Handshake_Key, неотличимы от шума      │
├─────────────────────────────────────────┤
│              Слой 3: Груз (Cargo)        │
│  CCLH_DATA, 8 потоков,                  │
│  зашифрован на Session_Key              │
└─────────────────────────────────────────┘

```

### 4.3. Схема взаимодействия

```

Client                          Server
│                               │
│── KTC0 (156 байт шума) ──────▶│
│                               │
│◀── KTCA (108 байт шума) ──────│
│                               │
│=== CCLH_DATA (потоки 1..7) ===▶│
│◀== CCLH_DATA (потоки 1..7) ===│
│                               │
│── CCLH_HALT (шифр) ──────────▶│
│                               │
X       (тишина)               X

```

### 4.4. Модель потоков

```

Одно соединение KTC v2.0
│
├── Stream 0: Управление (SACK, MASK_TRIGGER, ALIVE)
├── Stream 1: Данные
├── Stream 2: Данные
├── ...
└── Stream 7: Данные

```

Каждый поток — независимая последовательность `Cargo_Seq`, независимый BBR-контроллер.

## 5. Криптографическая система

### 5.1. Иерархия ключей

```

Root_Key (256 бит, offline, в TPM)
│
├── Handshake_Key = BLAKE2b(key=Root_Key, context="KTCv2.0-Handshake")
│
├── Legend_Key    = BLAKE2b(key=Root_Key, context="KTCv2.0-Legend")
│
└── (после рукопожатия)
Shared_Secret = X25519(Client_Priv, Server_Pub)
Session_Key   = BLAKE2b(key=Shared_Secret, context="KTCv2.0-Session")

```

### 5.2. Root_Key

- 256 бит, генерируется при регистрации
- Хранение: TPM / Secure Enclave (клиент), защищённая БД (сервер)
- Никогда не передаётся по сети
- Разблокируется паролем на клиенте

### 5.3. Handshake_Key

- 256 бит
- Шифрует KTC0 и KTCA
- Уникален для клиента

### 5.4. Legend_Key

- 256 бит
- Используется для Legend_Sig и Legend_Proof

### 5.5. Session_Key

- 256 бит
- Уникален для каждой сессии
- Используется для всех Cargo Frame

### 5.6. Алгоритмы

| Примитив | Назначение | Стандарт |
|----------|------------|----------|
| ChaCha20-Poly1305 | AEAD-шифрование | RFC 8439 |
| X25519 | Обмен ключами | RFC 7748 |
| BLAKE2b | Хеширование, KDF | RFC 7693 |
| HMAC-SHA256 | Подписи легенды | RFC 2104 |
| zstd | Сжатие | RFC 8878 |
| TPM 2.0 | Аппаратная привязка | ISO/IEC 11889 |

### 5.7. Отличия v2.0

- **BLAKE3 → BLAKE2b.** BLAKE3 требовал отдельной зависимости. BLAKE2b есть в libsodium. Производительность практически идентична для наших задач.
- **`explicit_bzero()` после каждого использования ключей.** Не даём компилятору оптимизировать очистку.
- **`mlock()` для ключевых структур.** Ключи не попадают в swap.
- **`crypto_verify_*()` для всех сравнений.** Защита от timing-атак.

## 6. Форматы пакетов

### 6.1. Cargo Offer (KTC0)

**Фиксированный размер — 156 байт.**

```

Открытая структура:
┌─────────┬──────────────┬────────────────┐
│ Nonce   │  Ciphertext  │  Poly1305_Tag  │
│ 12 байт │  128 байт    │  16 байт       │
└─────────┴──────────────┴────────────────┘

Внутренняя структура (128 байт):
┌────────────┬─────────────────┬────────────┬───────────────┬─────────────┐
│ Timestamp  │ Client_X25519   │ TPM_Quote  │ HW_MAC_Proof  │ Legend_Sig  │
│ 8 байт     │ 32 байта        │ 32 байта   │ 32 байта      │ 24 байта    │
└────────────┴─────────────────┴────────────┴───────────────┴─────────────┘

```

**Поля:**
- `Timestamp` — uint64, миллисекунды с эпохи UNIX
- `Client_X25519` — эфемерный публичный ключ клиента
- `TPM_Quote` — подписанная TPM-цитата
- `HW_MAC_Proof` — `HMAC-SHA256(Device_Secret, eth0_MAC || "KTCv2.0-HW-Bind")`
- `Legend_Sig` — `HMAC-SHA256(Legend_Key, Timestamp || Client_X25519 || TPM_Quote || HW_MAC_Proof)`

### 6.2. Cargo Accept (KTCA)

**Фиксированный размер — 108 байт.**

```

Открытая структура:
┌─────────┬──────────────┬────────────────┐
│ Nonce   │  Ciphertext  │  Poly1305_Tag  │
│ 12 байт │  80 байт     │  16 байт       │
└─────────┴──────────────┴────────────────┘

Внутренняя структура (80 байт):
┌────────────────────┬─────────────────┬───────────────┬──────────────┐
│ Echoed_Timestamp   │ Server_X25519   │ Server_Proof  │ Mask_Profile │
│ 8 байт             │ 32 байта        │ 32 байта      │ 8 байт       │
└────────────────────┴─────────────────┴───────────────┴──────────────┘

```

**Поля:**
- `Echoed_Timestamp` — копия Timestamp из KTC0
- `Server_X25519` — эфемерный публичный ключ сервера
- `Server_Proof` — `HMAC-SHA256(Legend_Key, Server_X25519 || Echoed_Timestamp)`
- `Mask_Profile` — uint64, ID профиля (0–11)

### 6.3. Cargo Frame (CCLH_DATA / CCLH_HALT / CCLH_ALIVE)

```

Внутренняя структура (до шифрования):
┌───────────┬───────────┬─────────────┬─────────────┬─────────┐
│ Cargo_Seq │ Stream_ID │ Frame_Flags │ Payload_Len │ Payload │
│ 4 байта   │ 1 байт    │ 1 байт      │ 2 байта     │ N байт  │
└───────────┴───────────┴─────────────┴─────────────┴─────────┘

```

**Frame_Flags:**
```

Бит 0: EXT_LENGTH     — Payload_Len расширяется до uint32
Бит 1: COMPRESSED     — payload сжат zstd
Бит 2: SACK_PRESENT   — содержит Selective ACK
Бит 3: MASK_TRIGGER   — смена профиля маскировки
Бит 4: HALT           — честное закрытие
Бит 5: ALIVE          — keepalive
Биты 6-7: зарезервированы

```

**Шифрование:**
```

Nonce = (Stream_ID << 32) | Cargo_Seq
ChaCha20-Poly1305(Session_Key, Nonce, inner)

```

**Nonce не передаётся открыто.** Снаружи — сплошной криптографический шум.

### 6.4. SACK-блок

```

┌────────┬──────────┬──────────────────────┐
│ Count  │ ACK_Seq  │ SACK_Blocks          │
│ 2 байта│ 4 байта  │ (Start+End)*Count    │
└────────┴──────────┴──────────────────────┘

```

- `Count` — 1..128
- `ACK_Seq` — последний непрерывный Seq
- `SACK_Blocks` — до 128 диапазонов

## 7. Процедуры

### 7.1. Установление соединения — Клиент

```

1. Разблокировать Root_Key из TPM (пароль пользователя)
2. Вычислить Handshake_Key = BLAKE2b(Root_Key, "KTCv2.0-Handshake")
3. Вычислить Legend_Key    = BLAKE2b(Root_Key, "KTCv2.0-Legend")
4. Сгенерировать эфемерную пару X25519
5. Получить TPM_Quote от TPM устройства
6. Вычислить HW_MAC_Proof
7. Вычислить Legend_Sig
8. Сформировать внутренний payload KTC0 (128 байт)
9. Сгенерировать случайный nonce (12 байт)
10. Зашифровать на Handshake_Key
11. Отправить датаграмму (156 байт)
12. Перейти в Cargo Pending, запустить таймер 5 сек

```

### 7.2. Установление соединения — Сервер (слепой приём)

```

1. Принять UDP-датаграмму p на GUARD_PORT
2. Если len(p) != 156 → DROP (тишина)
3. Для каждого CLIENT_ID в БД:
   а. Извлечь Handshake_Key
   б. Попытка расшифровки
   в. Если успех:
   · Проверить Timestamp (окно ±30 сек)
   · Проверить Legend_Sig
   · Проверить TPM_Quote (в production)
   · Проверить HW_MAC_Proof (в production)
   · Сгенерировать Server_X25519
   · Вычислить Server_Proof
   · Выбрать Mask_Profile
   · Сформировать внутренний payload KTCA (80 байт)
   · Зашифровать на Handshake_Key
   · Отправить KTCA (108 байт)
   · Вычислить Session_Key
   · Инициализировать 8 потоков
   · Перейти в Cargo Flow
   · ВЫХОД
4. Ни один ключ не подошёл → DROP (тишина)

```

### 7.3. Приём KTCA — Клиент

```

1. Принять UDP-датаграмму от SERVER_IP:GUARD_PORT
2. Если len(p) != 108 → DROP
3. Попытка расшифровки на Handshake_Key
4. Если не удалось → DROP (инжект ТСПУ)
5. Проверить Echoed_Timestamp
6. Проверить Server_Proof
7. Вычислить Session_Key
8. Прочитать Mask_Profile
9. Инициализировать 8 потоков
10. Перейти в Cargo Flow

```

### 7.4. Передача данных (Cargo Flow)

**Отправитель:**
```

1. Разбить данные на блоки по 65535 байт
2. Распределить round-robin по потокам 1..7
3. Для каждого потока:
   а. Сжать zstd (если включено)
   б. Сформировать Cargo Frame
   в. Cargo_Seq++
   г. Зашифровать ChaCha20-Poly1305
   д. Отправить датаграмму
4. Поток 0: SACK каждые 16 фреймов или 10 мс

```

**Получатель:**
```

1. Принять датаграмму
2. Попытка расшифровки на Session_Key
3. Не расшифровалось → DROP
4. Проверить Cargo_Seq > последнего
5. Обработать SACK (если есть)
6. Декомпрессия (если COMPRESSED)
7. Сменить профиль (если MASK_TRIGGER)
8. Собрать блоки
9. Передать上层 приложению

```

### 7.5. Закрытие соединения

**Честное:**
- Cargo Frame с флагом `HALT`
- Payload пустой
- Шифруется как обычный фрейм
- Получатель подтверждает

**Таймаут:**
- 30 секунд молчания → локальный разрыв
- Keepalive каждые 15–25 секунд

## 8. Производительность

### 8.1. BBR-контроль потока

| Фаза | Описание | Длительность |
|------|----------|--------------|
| Startup | Экспоненциальный рост | До первой потери |
| Drain | Сброс очереди | 1 RTT |
| ProbeBW | Циклическое зондирование | 8 фаз |
| ProbeRTT | Измерение базы RTT | Каждые 10 сек |

```

BW = max(доставленные_байты / интервал) за 8 окон
RTT_min = min(RTT) за 10 сек
CWND = BW * RTT_min * gain

```

### 8.2. Многопоточность

- 8 потоков, ID 0–7
- Поток 0 — управляющий
- Потоки 1–7 — данные
- Распределение: блоки по 64 KiB round-robin

### 8.3. Сжатие

- zstd, уровень 3 по умолчанию
- Флаг `COMPRESSED = 1`

### 8.4. SACK

- Каждые 16 фреймов или 10 мс
- До 128 диапазонов
- Retransmit только отсутствующих

## 11. Безопасность

### 11.1. Защита от атак

| Атака | Защита |
|-------|--------|
| Пассивный перехват | Шум, неотличимый от QUIC |
| DPI-сигнатура | Нет открытых тегов |
| TCP RST | UDP, нет флагов |
| ICMP | Игнорируется |
| Сканирование порта | Слепой сервер |
| Инжект KTC0/KTCA | Не расшифруется без ключа |
| Replay | Timestamp + Cargo_Seq |
| Подмена MAC | HW_MAC_Proof через TPM |
| MITM | X25519 + Legend_Sig |
| Корреляция сессий | Новые ключи на каждую сессию |
| DoS-флуд | Быстрый ChaCha20 decrypt |

### 11.2. Механизмы v2.0

- **`explicit_bzero()`** после каждого использования ключей
- **`mlock()`** — ключи не попадают в swap
- **`crypto_verify_*()`** — сравнения за константное время
- **Никаких логов ошибок** — DPI не узнает о попытках
- **Fork-безопасность** — RNG переинициализируется после fork
